# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

PrikBoard is a board of cards for small project management. It has a .NET 10 REST API (`src/PrikBoard.Api`) and a React 19 + Vite SPA (`src/web`). People in the browser and AI agents both use the same API, and the OpenAPI document at `/openapi/v1.json` is the contract between them. Background reading: `docs/architecture.md` (design and open decisions) and `docs/api.md` (endpoint table and conventions).

## Commands

```bash
docker compose up -d                              # PostgreSQL 17 on localhost:5432 (user/password/db: prikboard), data in volume postgres-data
dotnet run --project src/PrikBoard.Api            # API on http://localhost:5080; applies migrations on startup
dotnet test PrikBoard.slnx                        # all API tests (what CI runs); needs the compose database
dotnet test PrikBoard.slnx --filter "FullyQualifiedName~Moving_a_bucket_carries_its_cards_along"   # one test

cd src/web && npm install && npm run dev          # SPA on http://localhost:5173, proxies /api and /openapi to :5080
cd src/web && npm run lint                        # oxlint (CI)
cd src/web && npm run build                       # tsc -b type check + vite build (CI)

dotnet tool restore                               # pinned dotnet-ef from .config/dotnet-tools.json
dotnet ef migrations add <Name> --project src/PrikBoard.Api --output-dir Data/Migrations
```

No local Node here: run web checks in Docker, e.g. `sg docker -c 'docker run --rm -u "$(id -u):$(id -g)" -e npm_config_cache=/tmp/.npm -v "$PWD/src/web":/app -w /app node:22 sh -c "npm run lint && npm run build"'` (the `web-docker` launch config runs the dev server the same way).

`dotnet run --project src/PrikBoard.Discord` runs the Discord bot (needs `Discord:BotToken`, `PrikBoard:ApiUrl`, `PrikBoard:PublicUrl`; or `docker compose --profile discord up -d`). The link-preview PNGs in `src/web/public` are rendered from `src/web/icons` (see its README).

`.claude/launch.json` defines `api` and `web` preview servers. The frontend has no test suite. Set `PRIKBOARD_API_URL` to point the Vite proxy at a different API.

## Architecture

Terms: **Boards > Buckets > Cards**. What sits on a card is a *component* (Text, Checklist or Links; the UI calls a Text component a *note*), an image or a drawing. Use these words everywhere (code, API, MCP tools, UI text, docs): never note, post-it (a brand name), block or frame, and spell color the US way. The `CardsAndComponents` migration renamed the old `Notes` table and its `Blocks` column in place and rewrote stored `/notes/` links to `/cards/`; older migrations and the tests that seed them (`*MigrationTests`) still use the old names on purpose, and `/#/boards/{board}/notes/{n}` links no longer open.

Domain: a board is a freeform canvas. `Board 1──* Bucket` (named rectangles) and `Board 1──* Card` (200×120 px cards at x/y), and each card has an optional `BucketId`. A card also has tags, assignees, an `AgentWorking` flag, a creator (`CreatedById`, null for older cards) and its content as `Components` (`Domain/CardComponent.cs`: Text, Checklist or Links, each with an optional title and x/y/width/height on the card's own canvas). Tags and assignees are arrays (`PrimitiveCollection`) and always replaced as whole lists. Components are one jsonb column (`Data/CardComponentsJson.cs`, a value converter) and are changed one at a time through `CardComponentEndpoints` (addCardComponent, updateCardComponent, deleteCardComponent), which lock the card row so concurrent edits of different components survive. `Board 1──* BoardTag`: the board's tags, each with a `Color` (`TagColor`; Default is a shade of the card's fill, the others solid chips, mirrored in `index.css` as `.tag-color-*`). Cards store tag *names*; a new name on a card joins the board (`TagEndpoints.EnsureBoardTagsAsync`), and renaming or deleting a tag rewrites every card in one transaction. Assignees are principal ids (`Card.AssigneeIds`), shown with the principal's current name; only `BoardAccess.AssignableIds` (members plus their token agents that reach the board) can be added, but ids already on a card may stay. A new board gets the buckets *To do*, *Doing* and *Done* side by side (`Board.DefaultBuckets`). `Board 1──* BoardImage`: images on the canvas (x/y, display width, height from the aspect ratio) or attached to a card (`CardId`, deleted and restored with it; x/y are then on the card's canvas, and updateImage's `cardId`/`detach` move it between the two); the file is a `StoredFile` (`BoardImage.FileId`, see Files below). `Board 1──* BoardDrawing`: freehand drawings on the canvas or on a card (`CardId`, like images), each one or more strokes that select, move and delete as one: the row keeps the place, size and one ink per stroke (`Colors`), `DrawingContent` the strokes (jsonb, `DrawingStrokesJson`), and `Revision` versions `contentUrl` (`?v=`). The web pen (`board/useStroke`) starts a drawing with the first stroke of a pen session and adds the rest (addDrawingStroke) until the pen is put down; undo takes a stroke off again (deleteDrawingStroke, the `stroke` undo target). A selected drawing scales from its corner handles and turns with the round handle above it (`DrawingView`, which previews with `reshapeStrokes` in `drawings.ts`, a mirror of `BoardDrawing.Transform`); transformDrawing bakes that into the points, so the box stays upright, and undo puts the old points back with setDrawingStrokes (the `shape` undo target). A board has optional agent rules (`Board.Rules`, Markdown, max `Board.RulesMaxLength`, plus `RulesUpdatedAt`): only owners set them (updateBoard), and they are the one board text MCP agents are told to follow rather than treat as data. Readable ids: a board has a `ShortId` (6 random Crockford base32 characters, unique, never changed, `Board.NewShortId`) and a `Key` (`Board.KeyFrom` its name at creation, owner-editable, not unique); a card has a `Number` per board, taken from `Board.NextCardNumber` in createCard's transaction (`TakeNumberAsync`, an UPDATE … RETURNING that locks the board row) and never reused (unique index on `(BoardId, Number)` including deleted cards). `CardDetail` shows `number`, `readableId` (`MPCT-415`) and `path` `/#/boards/{shortId}/cards/{number}`; `CardDetail.From` takes a `BoardRef` (short id and key) for them. The older path `/#/boards/{boardId}/cards/{cardId}` stays valid everywhere (`CardLinks.TryParse` reads both, `LinkedCard`); component writes store such links to the same board as the card's path (`CardComponentEndpoints.ShortenLinksAsync`), the `ReadableIds` migration rewrote existing ones, and exports write links to the board's own cards in the id form so `FollowLinks` can map them. Raise `BoardExport.CurrentVersion` with every change to the export file's fields: importBoard refuses a newer version, and fields it doesn't know (`UnknownFieldsAsync`, which reads the body again thanks to `BufferedBody`), naming the PrikBoard version that wrote the file (`appVersion`, from `AppVersion`); the web app shows that in a `NoticeDialog`.

### API (`src/PrikBoard.Api`)

- **Minimal APIs, not controllers.** There is one file per resource in `Endpoints/`, each exposing a `Map*Endpoints(this RouteGroupBuilder)` extension that `Program.cs` calls on the `/api` group. Handlers are private static methods that take `PrikBoardDbContext` directly; there is no service layer. They return `TypedResults` with `Results<...>` union return types, so OpenAPI lists the exact status codes.
- **Every endpoint needs `.WithName("camelCaseOperationId")`**, plus `WithSummary`/`WithDescription`. These names are the stable tool names for AI clients and generated clients. A test asserts that key operationIds exist (`OpenApi_document_exposes_named_operations_for_ai_clients`).
- **XML doc comments on `Contracts/` records become OpenAPI descriptions** (`GenerateDocumentationFile` is on, CS1591 is suppressed). Write them for an AI reader. Validation uses DataAnnotations on record properties (`[property: Required, StringLength(...)]`) through .NET 10's built-in `AddValidation()`. Errors are RFC 9457 problem+json.
- **Contracts are separate from entities.** Response records have a static `From(entity)` mapper. Don't return `Domain/` entities from endpoints.
- **The server owns the geometry** (`Domain/Layout.cs`). Coordinates snap to a 20 px grid (`Layout.Snap`). `Card.BucketId` and `BoardImage.BucketId` (images on the board) are kept by `Layout`, never set directly by a request: an item that moves itself joins the topmost bucket containing its centre (`Layout.Place`, buckets stacked by `Bucket.StackedAt` through `Layout.BackToFront`; lists, the default bucket and reading order use creation order, `Layout.InListOrder`), and then stays in it while buckets move, so moving a bucket onto another never moves items between them. Bucket changes only touch their own items: a move carries them (and `Layout.Release`s any left outside by `carryCardIds`/`carryImageIds`), a resize releases its items now outside it and adopts only loose ones (`Layout.Adopt`, `looseOnly`), a created or restored bucket adopts what it covers, a deleted one releases everything; a restored card or image is `Layout.Recheck`ed. Never recompute every item's bucket from geometry outside an import (`Layout.PlaceAll`). A card's own canvas has its own rules (`Layout.NextCardSpot`, `Layout.Clamp`, `Layout.OnCardCanvas`), mirrored in `layout.ts` too. Moving a bucket shifts its cards by the same delta; an `x`/`y` sent together with a size is a resize from a top or left corner or edge and leaves them (`resizeFrom` in `layout.ts` is the client side). createCard and moveCard take `bucketId` (the server picks `Layout.MakeRoomIn`, which grows a full bucket downwards), both `x` and `y`, or all three: then the card joins that bucket (`Layout.PlaceIn`, 400 unless it contains the card's centre). The web app names its front bucket that way (`cardPlace` in `BoardCanvas`, `bucketUnderCard`'s `front`) so a card dropped where buckets overlap joins the one shown in front even before the server has put it on top, and undo records a card's `bucketId` with its place. placeItemsInBucket (MCP `place_in_bucket`) puts cards, images and drawings into a bucket at once through `Layout.PackIn` (each at its own size, cards first, in the first free room on the 20 px grid, a grid step clear of the bucket's own and loose items, not its neighbors'; then growing towards a `GrowSide` only as far as needed, or across for an item too wide or tall, over neighboring buckets too since the items join by id, unlike `MakeRoomIn`'s card-sized slots, which skip buckets stacked above (of a collapsed one only its square) and ignore cards folded into other collapsed buckets; `packIn` in `layout.ts` mirrors it): the web app uses it when a group of selected items (no buckets) is dropped on a bucket they aren't all in (`arrangeFor` in `board/dropTargets.ts`, growing towards the edge nearest the pointer; that bucket is in front while dragging and after the drop), and when any item or such group is dropped on a collapsed one (`putItems` in `board/useBoardMoves.ts`, in the order of `bucketItemsOf`). Several selected cards also get a toolbar above them (`SelectionToolbar`) that sorts them into a grid where they are (`sortCards` in `board/useBoardMoves.ts`). `src/web/src/board/layout.ts` mirrors these rules for drag feedback, so keep the two in sync.
- **REST and MCP parity.** Every feature works through both. Where REST takes ids (`bucketId`, `assigneeIds`, tag ids), MCP tools also take names and resolve them before calling the REST handler. MCP tools take a `board` (id or short id) and a `card` (id, readable id, or either path form, also as a full link), resolved by `ResolveBoardAsync`/`ResolveCardAsync` *before* `McpCall.AuthorizeAsync`, so a missing board and one you can't see give the same "Not found"; a readable id is looked up among the caller's reachable boards only, since keys aren't unique.
- **PATCH semantics.** A null field means unchanged. Optional text fields go through `PatchText.Apply`, where empty or whitespace clears the value (sets it to null). A list that is given replaces the whole list (`ApplyLists` in `CardEndpoints`; a component's `items`/`links` in updateCardComponent). Tags are normalized by `CardTags.Normalize`, and links must be absolute http(s) URLs or another card's path in either form (`CardLinks`, `CardDetail.Path`). A component only takes the content of its kind (400 keyed on the field otherwise). Moving a card is a separate `POST /cards/{id}/move` (`moveCard`), not part of `updateCard`. Buckets move and resize through `updateBucket`.
- **Error shapes.** A bucket that isn't on the card's board, or an invalid `bucketId`/`x`/`y` combination, is a 400 `ValidationProblem` keyed on the field. Use 409 `TypedResults.Problem` for state conflicts.
- **Authentication** (`Auth/`, `docs/authentication.md`). Browsers sign in through a provider configured under `Auth:Providers` (generic OpenID Connect, plus a `GitHub` OAuth adapter) and get a cookie. `Auth:DefaultProvider` (github) is listed first. Machines send JWT access tokens (Client Credentials) from issuers under `Auth:Tokens:Issuers`; PrikBoard issues only its own personal access tokens. The fallback policy `AuthSetup.ApiPolicy` requires a caller and, for tokens, scope `boards:read` (GET/HEAD) or `boards:write` (everything), so public endpoints need `.AllowAnonymous()`, which also clears their OpenAPI `security`. `ClaimsPrincipal.IsToken()` tells tokens from sessions, and `UserId()` only works for sessions. Use `PrincipalId()` where both may occur. A token acts as an agent unless its client id is in the issuer's `UserClients` (the VS Code extension), in which case it acts as the `User` its `sub` maps to (`UserSignIn.ResolveUserIdAsync`), so `whoAmI` can return `kind: Token` with `principalKind: User`. There is no dev login. `/scalar` (Scalar API reference) uses `.RedirectToSignIn()` to send anonymous visitors through the default provider. Keep `changeOrigin: false` on the Vite proxy (`/api`, `/openapi`, `/scalar`), because OAuth callback URLs are built from the Host header. External identities are mapped to a `User` (via a hashed `UserIdentity`) in `UserSignIn.OnTicketReceived`, which also handles linking a second sign-in. In that event `context.Fail()` does not stop the sign-in, so reject with `HandleResponse()` and a redirect. Boards are members-only (see below).
- **Invite-only sign-up and admins.** `UserSignIn.SignInAsync` only creates a user for the very first sign-in (who becomes admin, `User.IsAdmin`) or when the return URL holds an open invite (`InviteTokenIn`, `InviteIsOpenAsync`); otherwise it returns null and the callback redirects with `invite_required`. Sign-ups take a PostgreSQL advisory lock. `ResolveUserIdAsync` (delegated tokens) never creates users. The test login passes `SignUp.Always` unless the test gives a `returnUrl`. `AdminEndpoints` (`/api/admin`, `RequireAdmin()`: sessions only, 403 otherwise, no MCP tools on purpose) list every board and user, delete any board, set or remove anyone's board role (reusing `MemberEndpoints.LockBoard`/`IsLastOwner`), toggle admins (always one left) and delete users (not themselves, not a board's only owner). Deleted users' cookies are rejected in `OnValidatePrincipal` via `UserState` (cached a minute; `UserState.Forget` and `AccessTokenHandler.Forget` on delete).
- **Users, members and personal data** (`Domain/Principal.cs`, `Auth/KeyedHasher.cs`, `Auth/BoardAccess.cs`):
  - Never store SSO names, emails or provider subject ids. A `User`/`Agent` (TPH `Principals`) is a GUID plus a self-chosen `DisplayName`.
  - Avatars are opt-out: `UserSignIn.SignInAsync` downloads the GitHub picture (`ProviderAvatars.TakeAsync`, trusted hosts only) into a `StoredFile` (`User.AvatarFileId`) on every sign-in unless `User.AvatarOptedOut` (set by removeAvatar, cleared by useSignInAvatar). Only the copy is stored, never the URL (it holds the GitHub account id); the URL rides in the cookie (`UserPrincipal.SuggestedAvatarClaim`). `AvatarUpdatedAt` only changes when the bytes do (compared by `StoredFile.Sha256`), since it versions `avatarUrl`. Contracts expose `avatarUrl` via `Avatars.UrlOf`, and the web shows it with `components/Avatar`'s `Face`. Tests fake the avatar host in `PrikBoardApiFactory` (`GitHubAvatar`, `TestAvatar`, and `OtherGitHubAvatar` for a changed picture).
  - `UserIdentity` keeps only `KeyedHasher` HMACs (key `Auth:HashKey`) of the subject and verified email.
  - Code that serves both people and tokens uses `PrincipalId()`. `UserId()` is for sessions only.
  - Token clients become `Agent`s in `OnTokenValidated` (`AgentRegistry`).
  - Boards are members-only (Owner/Editor/Viewer). **Every `/api` endpoint declares `.RequireBoardRole(role, BoardScope.X)` or `.NoBoardScope()`**; a test fails otherwise. The filter answers 404 to non-members and 403 to low roles, and handlers read the role with `HttpContext.BoardRole()`.
  - Public boards (`Board.IsPublic`, owner-set through updateBoard): Viewer reads marked `.AllowVisitors()` (getBoard, getBoardByShortId, getBoardAvatar, image and drawing content; policy `AuthSetup.PublicReadPolicy` instead of the fallback) also answer non-members, signed in or anonymous but never tokens, as a Viewer with `HttpContext.IsBoardVisitor()`. Handlers must not touch `PrincipalId()` for anonymous callers. Visitors get `BoardDetail.ForVisitors` (no people; assignees and creators anonymous unless `PublicShowsPeople`, then avatars through getBoardAvatar). Live: anonymous connections are allowed (same origin); visitors join `BoardHub.VisitorGroup`, get `BoardChanged` (by `Guid.Empty`) and presence (`LiveViewers.Presence`, members listed or only counted), never drags; `BoardEvents.VisitorsChangedAsync` sends them `AccessChanged` when the board's public settings change. The web app shows a public board to non-members in `components/VisitorPage` (from `App` when signed out, or from `Workspace` when the board isn't in your list).
  - Membership changes lock the board row (`MemberEndpoints.LockBoard`) so a board always keeps an owner.
  - Email lookup, invite accept/preview and linking are sessions only.
  - Tests: `factory.CreateSignedInClientAsync(...)`, `TestLinkAsync`, and `TestApi` helpers (`MeAsync`, `CreateBoardAsync`, `ShareAsync`).
- **Personal access tokens and MCP**:
  - `Bearer pb_pat_...` goes to the `pat` scheme (`AccessTokenHandler`). The token acts as its own `Agent` (issuer `pat`), with its owner's memberships capped and limited by `BoardCaller` (`Auth/AccessTokens.cs`).
  - Use `BoardCaller.Of(principal)` or `BoardAccess.RoleOnBoardAsync(db, boardId, principal, ct)` for any new board-role lookup; never query `BoardMembers` by `PrincipalId()` directly.
  - A token of kind `App` (from the VS Code extension's sign-in, `Endpoints/AppSignInEndpoints.cs`: PKCE code from the `#/connect` page, `components/ConnectPage.tsx`) has no agent and acts as its owner (`PrincipalClaim` = owner, no cap claims), so `AccessToken.AgentId` is nullable.
  - Token management endpoints are sessions only.
  - `/mcp` (`Mcp/BoardTools.cs`, a partial class with its resolvers in `BoardTools.Resolve.cs` and result records in `ToolModels.cs`; policy `AuthSetup.McpPolicy`: bearer only, Origin check) calls the `internal` REST handlers after `McpCall.AuthorizeAsync`, validates with `McpCall.Validate`, and must `McpCall.AnnounceAsync` after writes. `AnnounceAsync` also marks the call as a write, so the `McpCall.RulesReminder` call-tool filter appends a reminder of the board's rules (with `RulesUpdatedAt`) as a second text block; tests parse the first block.
  - Image files go through upload URLs, not tool arguments: `begin_image_upload` (REST createImageUpload) stores an `ImageUpload` (placement, caller, `MemberId`/`Cap`, `AccessTokenId`; hash of a `pb_upl_` token, 15 minutes) and the agent runs `curl -T` to `PUT /api/image-uploads/{token}` (completeImageUpload, `.AllowAnonymous()`: the URL is the key). It locks the row, re-checks access (`StillAllowedAsync`), and spends the URL only with a saved image, so a 413/415 can be retried. `add_image` (base64) stays for tiny images: a model writes base64 out character by character.
  - Tool errors are `McpException`s.
  - Tools that take a `board` fall back to the token's only board (`ResolveBoardAsync`). `McpCall.AuthorizeAsync` records the caller's last board (`Mcp/LastBoard.cs`, `Principals.LastBoardId`), and `ConfigureSessionOptions` names it in the server instructions with its buckets, tags and rules (`LastBoard.BriefAsync`, cached a minute per board; `McpCall.ForgetRules` drops it and the reminder's cached timestamp when updateBoard changes the rules). Stateless MCP runs that hook on every request, so it sets the instructions from the fixed `mcpInstructions` and never appends.
  - MCP read results are trimmed for agents: `CardSummary`/`BucketOverview`/`BoardPersonSummary` leave out empty lists and false flags (`bool?` null, `WhenWritingNull`), show assignees by name, and only count the cards of collapsed buckets. Card tools return `CardView` (bucket by name, components without canvas geometry, their content only from get_card), not `CardDetail`. Keep new fields there in that style.
  - MCP tools need `JsonSerializerOptions` with a `TypeInfoResolver` (`McpCall.Json`).
  - Tests: `AccessTokenTests`, and `McpTests` with the official MCP client over the test server.
- **Discord link previews** (`docs/discord.md`, `Endpoints/DiscordEndpoints.cs`, bot in `src/PrikBoard.Discord`). A connected Discord server is an `Agent` (issuer `Agent.DiscordIssuer`, client id the guild id, row `DiscordGuild`) that is a Viewer member of each connected board; `DiscordBoardChannels` narrows where (channels, or null for the whole server). Its token is `AccessTokenKind.Discord`: the agent's own memberships, `boards:read` only, a `KindClaim` that `AuthSetup.DiscordPolicy` requires on the bot's endpoints (getLinkPreview, getDiscordStatus, revokeDiscordToken). Connecting is the App sign-in paste flow (approveDiscordConnect from `#/connect/discord`, exchangeDiscordConnect from the bot). getLinkPreview answers the same 404 for everything it won't preview, and matches links against `Discord:PublicUrl`; `CardPreview.Describe` builds descriptions. Discord servers are never assignees (`AssignableIds`). The bot talks to the API over HTTP only and keeps each server's token encrypted (Data Protection) under its own `Storage:Path`.
- **Live updates** (`Live/`, SignalR hub `BoardHub` at `/api/live`, policy `AuthSetup.LivePolicy`, which also checks the Origin of cookie connections):
  - The `RequireBoardRole` filter announces successful board-scoped writes (`BoardChanged`) itself. Mark board-scoped POSTs that change nothing with `.Quiet()`. Changes to board lists, roles or names call `BoardEvents` explicitly (`BoardsChangedAsync`, `AccessChangedAsync`, `RenamedAsync`).
  - Presence and roles of open connections live in the `LiveViewers` singleton (one instance only). SignalR user ids are principal ids (`PrincipalUserIds`).
  - The web app sends its connection id as `X-PrikBoard-Live` on changes, so it is not told about its own changes.
  - Tests use the SignalR client over long polling against the test server (`LiveApiTests`), with the session cookie and an `Origin` header.
- **Soft delete and restore** (`Data/Tombstones.cs`). Deleting a card, bucket, image or board tag sets `DeletedAt`; the named query filter `PrikBoardDbContext.SoftDelete` hides it everywhere, so `FindAsync` and queries just return 404 for it. restoreCard, restoreBucket, restoreImage and restoreBoardTag (MCP: `restore_card`, `restore_tag`) bring it back with the same id within `Tombstones.Retention` (7 days); `TombstonePurger` deletes older ones for good every hour. A card's images share its `DeletedAt` and come back with it. A deleted tag keeps `RemovedFromCardIds`. Bypass the filter with `IgnoreQueryFilters([PrikBoardDbContext.SoftDelete])` (restores, `BoardAccess.AuthorizeAsync`, the purge); raw SQL never applies it, so the tag rename/delete SQL also rewrites deleted cards. Boards and users stay hard deletes. For undo, updateBucket takes `carryCardIds` (a move carries exactly those cards) and addCardComponent an `id` (put a removed component back).
- **Files** (`Domain/StoredFile.cs`, `Data/FileStore.cs`). Image and avatar bytes are never in the database: they are files under `Storage:Path` (a volume of its own in production; Development defaults to `src/PrikBoard.Api/files`, and the API won't start elsewhere without it), named after the `StoredFile` id, never after `FileName`, which the row keeps for Content-Disposition: a board's images in `boards/{boardId}/{id}` (`StoredFile.BoardId`, not a foreign key, never changes), avatars in `avatars/{id}`. Get paths from `FileStore.PathOf(file)`. Content never changes for an id: new content is a new file. Write the file (`FileStore.WriteAsync`) before saving, and only insert a `StoredFile` together with the row that refers to it (`Images.FileId`, `Principals.AvatarFileId`, one-to-one, `Restrict`); a failed save then leaves at most a file without a row. Nothing deletes files inline: `FileStore.SweepAsync`, run hourly after the purge, deletes rows nothing refers to (deleted boards and users, purged images, replaced or removed avatars; soft-deleted images keep theirs), files without a row older than a day, and board folders empty for a day. Serve them with `StoredFileResults.ServeAsync` (ETag = file id, immutable, ranges; files up to `Storage:MemoryCacheMaxFileBytes` from the store's own memory cache). Load `i.File` explicitly where an `ImageDetail` is built. `StartupMigration.RunAsync` (Program.cs) migrates up to `StoredFiles`, moves bytes left in the old bytea tables to disk (into board folders already; `StoredFileBoards` then fills in `BoardId`), then runs the rest; `DropDatabaseBlobs` refuses while any are left, so plain `MigrateAsync()` in tests only works on databases without images. Tests get a temp folder per factory (`FilesPath`, `SweepFilesAsync`, `ImageFileAsync`, `AvatarPathAsync`).
- **Deleted items and collapsed buckets.** Deleted items (the trash) are the soft-deleted cards below: listDeletedCards (`GET /boards/{id}/trash`, newest first, with the images that share each card's `DeletedAt`) feeds `board/TrashWindow`, a floating window like the expanded card, opened from the board menu ("Deleted items") through `#/boards/{id}/trash`. It lays cards out with `fitGrid` and searches them with `board/search.ts`; they go back with restoreCard, at `x`/`y` when dragged out, and a card dragged onto the window is deleted, like one dropped on the rail's trash can. purgeCard (`DELETE /boards/{id}/trash/{cardId}`, a card's trash button there) and emptyTrash (`DELETE /boards/{id}/trash`, *Empty trash* in its band, after a `ConfirmDialog`) delete for good, with no undo step; the cascades take the images and drawings. The expanded card always sits above the trash window. `Bucket.Collapsed` folds a bucket into a `Layout.CollapsedBucketSize` square in its top-right corner (`collapsedRect` in `layout.ts`; the fold button sits in that corner in both states): its cards and images keep their places and `BucketId` but the web app hides them. A collapsed bucket takes no other items (`Layout.TopmostAt` and `Adopt` skip it, mirrored by `bucketUnderCard`'s `own`), except items put into it by id (dropped on the square: placeItemsInBucket, or a card's `bucketId`). It moves, carrying its items, but can't be resized. How buckets stack is shared (`Bucket.StackedAt`, `stackedAt` on `BucketDetail`, which lists buckets in creation order): updateBucket puts a bucket on top when it moves, resizes or opens (`Bucket.ToFront`), placeItemsInBucket when it fills it, and bringBucketToFront (MCP `bring_bucket_to_front`) when the web app's user presses it (`toFront` in `BoardCanvas`, which also shows it in front at once as `picked`, and only there for viewers). The web app draws buckets in that order (`backToFront` in `layout.ts`) and the topmost open one with its items above the rest (`front`, `.in-front`; its fill covers what lies under it). Exports carry each bucket's place in the stack (`ExportedBucket.Stack`).
- **Card history** (`Domain/CardChange.cs`, `Data/CardHistory.cs`). Every save made for a signed-in caller records a `CardChange` (who, when, a jsonb list of `CardChangeEntry`) per card it changed: the `CardHistory` `SaveChangesInterceptor` (sync and async saves) diffs tracked `Card`s and the `BoardImage`s and `BoardDrawing`s on cards against their original values, so handlers record nothing themselves. Paths that bypass the tracker (`ExecuteUpdate`, as in deleteCard, deleteImage and deleteDrawing) call `CardHistory.Record` and save. Not recorded: moves within a bucket, component/image/drawing geometry, cards added with their board (import), and the tag rename/delete SQL. Title, color and component edits by the same caller within `CardHistory.MergeWithin` merge into one change (and vanish when put back); a title or color right after creating is part of the Created change. Kinds are stored as strings; one this version doesn't know reads as `Other` (`CardChangesJson`), so never rename a kind. listCardHistory (MCP `get_card_history`) is members only and works for deleted cards too; purging a card takes its history. In the web app, `board/CardHistory` is a sheet along the bottom of the expanded card (not for visitors, not in the mobile layout yet): folded to a bar at first, the bucket fold button slides it up over the canvas (which keeps its size).
- **Copy and paste** (`Endpoints/ClipEndpoints.cs`, `Contracts/Clips.cs`). copyItems turns cards, buckets (with what is in them) and loose images and drawings into a `BoardClip`: a self-contained piece of JSON like a cut-down export (cards with components, tags and assignee ids, images as base64, drawings, buckets back to front, tag colors, and `source`: server URL from the request's Host, board short id and key; items name their copied bucket by `bucketId`, and `ClippedImage`/`ClippedDrawing` extend the export's records). pasteItems adds a clip as new items, moving everything by one step from the clip's top-left to `x`/`y`: items join their pasted bucket by id (never by geometry), others are `Layout.Place`d, pasted buckets go on top and then take the loose items they cover (`Adopt`, `looseOnly`, not when folded). It is checked like importBoard (newer `version` or unknown fields refused through `BufferedBody`), so a clip pastes on any PrikBoard server; MCP `copy_to_board` does both on the server. Raise `BoardClip.CurrentVersion` with every change to its fields. Links between pasted cards follow the copies; other card links stay on the same server and become full URLs to the source server otherwise. Each copy's history is one `Copied` entry (the interceptor skips Created, and attachments added with a new card). Cut (`cut` on the clip, Ctrl/Cmd+X, MCP `move`): pasted on another board of the same server, `RemoveOriginalsAsync` soft-deletes the originals still there in the paste's transaction (Editor on their board; history `Moved`/`MovedAway`) and returns them as `moved`; the web app records them as deleted changes with a `boardId`, so undo (`otherBoards`, `check`/`apply` with `elsewhere`) loads that board and restores them there. Cut and paste on the same board is a plain group move in the web app (`moveCutHere` in `board/useBoardClipboard.ts`, `moveGroup`'s `by`), keeping ids and numbers; the server refuses it. The web app writes the clip to the system clipboard in `text/html` (a `data-prikboard-clip` attribute under a readable list) plus plain text (`board/clipboard.ts`, falling back to the copy command where the async clipboard is refused, as in the desktop app's browser pane), reads it back in the board's paste handler, and duplicates (Ctrl/Cmd+D) through the same two calls.
- **PostgreSQL specifics** (Npgsql). `DateTimeOffset` maps to `timestamp with time zone`, which only accepts UTC offsets and keeps microsecond precision, so always use `DateTimeOffset.UtcNow` and use `AddMilliseconds`, not ticks, to separate timestamps. Card tags are a `text[]` column and assignee ids a `uuid[]`; components are `jsonb` (camelCase names; hand-written migration SQL must match them). Card search (listCards) filters title and component text in memory, like tags and assignees. Npgsql's EF Core packages lag the Microsoft ones, so the API pins `Microsoft.EntityFrameworkCore.Relational` to the same version as `Microsoft.EntityFrameworkCore.Design`; without it the tests fail with CS1705. Migrations run automatically on startup. JSON uses `JsonNumberHandling.Strict` to keep the OpenAPI integer types clean. Enums are serialized as strings (`CardColor` fills are Butter, Mint, Sky, Coral and Lilac).

### Tests (`src/PrikBoard.Api.Tests`)

The tests are xUnit integration tests over HTTP only. `PrikBoardApiFactory` (a `WebApplicationFactory<Program>`) gives each test class its own PostgreSQL database `prikboard_tests_<guid>` on the compose server (override the server with `PRIKBOARD_TEST_POSTGRES`), dropped in `DisposeAsync`. CI runs the same image as a service container. Tests run in a `Testing` environment (no user secrets) with the GitHub client id from appsettings.json cleared, so they start without sign-in providers; test factories add the providers they need with `UseSetting`. Tests in a class share that database, so each test creates its own board and doesn't assume global state. Every `/api` call needs auth: use `factory.CreateSignedInClientAsync(email)`, which signs in through a test-only middleware the factory adds (the API has no sign-in shortcut), or a JWT from the in-memory issuers in `TokenAuthTests`.

### Web (`src/web`)

- `src/api/types.ts` contains **hand-written** mirrors of the C# contracts, and `src/api/client.ts` has one method per operationId with the same name. They are not generated. When you add or change an endpoint or contract, update both, plus the endpoint table in `docs/api.md`. The VS Code extension (`src/vscode`) bundles these two files too, so keep them free of DOM and React imports; `configureClient` sets its server and bearer token (the web app uses the defaults).
- `App` checks `whoAmI` and shows `SignIn` until there is a session, except for a board link, which first tries the board as a visitor (`VisitorPage`; signed out, it falls back to `SignIn`). Any 401 from `client.ts` goes back to sign-in (`setUnauthorizedHandler`). The signed-in user's initials, API reference link and sign-out live in the settings menu on the right of the top bar, plus *Admin* for admins (`#/admin`, `components/AdminPage`: people on the left are dragged with pointer capture onto a board's role zones or the Admins bucket, hit-tested through `data-drop` attributes; each list scrolls on its own, auto-scrolls while a drag nears its edge, and is searched in the browser).
- A board in the hash that isn't in `listBoards` is fetched once more, then opens as a visitor when it is public (`VisitorPage`), and else shows `components/NoAccess` (the sad page) instead of falling back to another board; losing access to the open board shows it too.
- The design is the "Night shift" mockup (`docs/Scrum Board — Night shift.html`): Geist fonts, a floating tool rail, a zoom/minimap corner, outlined buckets, cards showing title, tags and assignees, and an expanded card view (`board/ExpandedCard`).
- The expanded card's band shows who created it and when (`board/dates.ts`; the mobile `CardScreen` too), and its history sits at the bottom (`board/CardHistory`, see Card history above).
- The expanded card is a non-modal window over the board (`useFloatingWindow`, size and place in localStorage), with no backdrop: the board around it stays visible and usable. Inside, `CardCanvas` is a small board of its own (zoom via `useZoom`, gestures via `gesture.ts`, components in `CardComponents`, bar `CardBar` sharing the `.rail` look with the tool rail). Both canvases capture the pointer during a drag, so dragging an image between them hit-tests rectangles: `BoardCanvas` asks the window's `ExpandedCardHandle` (`hits`, `toCard`, `wantsPaste`), and `CardCanvas` asks the board for `boardPoint`. Releasing a dragged card with the pointer over another card, or over the open window, links it there instead of moving it (`linkDropFor` and `linkCards` in `board/dropTargets.ts`), and a board image dropped on a card is attached to it. Several selected items dragged together do the same (`dropGroup` in `board/useBoardDrops.ts`): cards only link (one link per card) or go into a collapsed bucket, images and drawings only are attached (`attachGroup`), and any group dropped on the trash can or the open deleted items is deleted like Delete does; mixed groups otherwise just move. Images are built (`board/BoardImageView`, `board/files.ts`); freehand drawing from the mockup is not.
- No state library and no UI kit. `board/useBoard` (used in `App`'s `Workspace`) loads the board and exposes `run()`, which calls the API and then reloads the full board. `live/useLive` keeps a SignalR connection: others' saves call `useBoard`'s `refresh()`, and polling drops from every 4 s to every 30 s while connected. Others' drags in progress come in as `remoteDrags` and are applied by the same geometry functions as your own gesture (`bucketRect`, `cardPoint`, `imageRect` from `board/liveGeometry.ts`). The Vite proxy has `ws: true` for the hub. `BoardCanvas` wraps it in `settle()`. While a pointer gesture is in progress it renders the snapped position locally (`Gesture`, in `board/boardGesture.ts`) and pauses polling. On drop it sends one request and keeps the gesture until the reload lands, so items don't jump back. Every press on an item captures the pointer on the canvas, so the browser sends `click` and `dblclick` to the canvas, not the item: `BoardCanvas` works out clicks itself (`cardPresses` for double-click to expand, `titlePress` for click-to-edit a title, with `caretAt` placing the text cursor).
- The canvas is scaled with a CSS transform for zoom. `toCanvas()` (`board/useBoardView.ts`) divides by the zoom. The board has no edge at 0,0 (coordinates run from `MIN_COORDINATE` to `MAX_COORDINATE`, as `Layout.MinCoordinate`/`MaxCoordinate` on the server): the canvas starts at its leftmost and topmost item (`low`, from `useCanvasExtent`, live while dragging), `origin` is where 0,0 sits, and when `low` changes the scroll position moves by as much so nothing on screen jumps. Around it is an empty `margin` of half the viewport on every side (so any part of the board can be scrolled to the middle when zoomed out), plus `RAIL_INSET` px on the left so the tool rail doesn't cover it. The margin keeps the scroll position in step when the viewport resizes; `.canvas::before` draws the dots over it and takes its presses. The wheel zooms the board (`useZoom` `wheel: 'always'`, smooth, per frame); Shift + wheel scrolls; the middle button pans, and so does a left press with Space held (`useSpaceHeld`, also in the card).
- **Selection** (`board/selection.ts`). Both canvases keep a list of selected items (`selected`; `selection` is the one item when exactly one is, for panels, resize handles and toolbars). Shift or Ctrl/Cmd + click toggles an item, and a drag on empty space draws a selection rectangle (a `select` gesture; with Shift or Ctrl/Cmd it adds to `base`). On the board, starting on the background it takes the buckets and loose items it touches (not what is in a bucket: moving the bucket carries it); starting inside a bucket, only that bucket's own items (a click there selects the bucket, and a bucket moves by its name or its rim, `.bucket-rim`). In the card a drag on empty canvas selects components, images and drawings (viewers still pan). Pressing one of several selected starts a `group` gesture: its `members` move by the same delta through the usual geometry functions (on the board, not items in a selected bucket, which carries them), dropped as one step (`moveGroup` in `board/useBoardMoves.ts`: buckets first, then the rest), and live as a `Group` drag listing `items`. Shaking a group of cards only (`board/shake.ts`, during the drag) lines them up in a grid around the one held (`gridFor` in `board/liveGeometry.ts`; the gesture's `grid` gives each its own drag delta); others see the plain group drag until it lands. Delete/Backspace with several selected deletes them all (`deleteSelected`/`removeSelected`, buckets too, keeping what is in them) as one step with a toast.
- Dark is the only theme. `:root` in `index.css` holds the color tokens.
- Scroll bars are themed in `index.css` (`::-webkit-scrollbar`, standard properties for Firefox only, since setting them makes Chrome ignore the webkit rules). The board and card canvases always show both bars (`overflow: scroll`) so their size never changes mid-gesture; floating controls keep `--scrollbar` clear of the edges.
- Markdown is rendered by `components/MarkdownView` (`react-markdown` + `remark-gfm`; raw HTML is never rendered, card links open in place, other links in a new tab). Keep it lazily imported so it stays out of the main bundle. Text components are Markdown: `TextComponent` shows it rendered and switches to a text area on click (not on a link or after selecting text); an empty component is always the text area.
- "Agent rules" in the board menu (under Rename board, in `App`) opens `components/BoardRulesDialog` (lazy-loaded, it renders with `MarkdownView`). Everyone reads the rules; owners edit them with Write/Preview tabs, and the draft is local state so live reloads don't overwrite it.
- **Undo/redo** (`board/undo.ts`, `board/useUndo.ts`). Every board change goes through `runRec`/`settle(action, describe)` in `BoardCanvas` (built by `recordingRun` and `settling` in `board/ops.ts`; several requests in one step go through `runAll`, which keeps the changes that went through when one fails; passed down as `run: RecordingRun` to `ExpandedCard` and `CardCanvas`); `describe(result)` builds the step from the item before (the `board` at the call site) and the response after, with `step`/`created`/`deleted`/`patched` and `snap.*`. Steps are plain data in `UndoHistory`, one stack per board, held by `App`'s `Workspace` (kept across board switches, gone on reload). Undo fetches the board, refuses with a reason (warn toast, step dropped) when a recorded field changed since, someone is dragging it or a restore can't work, and otherwise writes the old values back (deletes via the restore endpoints, so ids stay). Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z and Ctrl+Y work on the board and in the open card but not in fields (the browser's own text undo); the buttons sit next to the minimap (`ViewControls`). A new change needs a step at its call site, or it can't be undone.
- Deletes of cards, images, components, buckets and tags don't ask: they can be undone, and a step with `toast` shows a toast with an Undo button. Ask before other destructive actions (deleting a board, members) with `components/ConfirmDialog`, never `window.confirm`: embedded browsers such as the Claude desktop browser pane suppress native dialogs and answer "cancel", so the action silently never happens. A selected card or image is deleted with Delete/Backspace, or a card with the red trash button in the expanded card's bar; a selected component or image in the expanded card with Delete/Backspace too. Ctrl/Cmd+D duplicates the selected card one grid step down and right, with its images and drawings; Ctrl/Cmd+C copies the selection to the clipboard, Ctrl/Cmd+X cuts it, and Ctrl/Cmd+V pastes at the pointer (see Copy and paste).
- Tags and people are picked in `components/PickerWindow` (via `board/TagPicker`, `board/AssigneePicker`), from the card on the board or from the expanded view. It is portalled outside the zoomed canvas and keeps focus in its field; the canvas key handler ignores `[role="dialog"]`. `board/tags.ts` mirrors `CardTags.Normalize` and has `useDraftList`, which sends whole-list saves one after another. A tag's color circle in the tag window opens `board/TagColorPalette` (hover previews the color everywhere through `BoardCanvas`'s `tagColors`, built by `board/tagColors.ts`).
- The board search (`board/BoardSearch`, matching in `board/search.ts`) is client-side over the loaded board, not the `searchCards` endpoint (a prefix keeps a word to one field: `tag:`, `assignee:`, `creator:`, `color:` with fill names or plain color words; buckets holding matches, collapsed ones too, get `.search-hit`): `/` or Ctrl/Cmd+F opens it (not from fields, menus or other windows; the open card stays open, and while searching `.board-top.searching` sits above the windows so the results show over it; picking a result swaps the open card), and it combines with the filters at the bottom left (`board/TagFilter`, `board/AssigneeFilter` with `NOBODY` for unassigned cards, in `.board-filters`; a card stays bright when it passes each) through `BoardCanvas`'s `dimmed`. Words are marked with `board/Highlight`, which can't reach inside inputs and text areas (the open card's title, text components), so components with a match get an outline instead. While searching, the top margin grows to `SEARCH_MARGIN` so a card at the top can be scrolled below the results.
- Images are uploaded as the raw request body (`api.uploadImage` sends the `File` with its own content type), never as a form: a form encoding would let another site post with the session cookie, so `uploadImage` rejects them. The server sniffs the real format (`ImageFormats.Detect`); SVG is refused.
- The selected board lives in the URL hash (`#/boards/{shortId}`), and an expanded card adds `/cards/{number}` (`BoardCanvas` replaces the entry as it opens and closes, which also rewrites an address in the older id form; `board/links.ts`: `boardRefFromHash`/`isBoard` take either a board id or short id, `linksTo`/`linkedCard`/`cardInHash` either path form). The readable id (`MPCT-415`) in the expanded card copies that link, and a card on the board names it in the tooltip of its copy-link button. A link to a card is stored as its path without a host and opens in place. Owners change the key under *Change key* in the board menu.
- **Mobile layout** (`mobile/`, picked by `useLayoutMode` in `layoutMode.ts`: narrow touch screens, or Mobile/Desktop view in the settings menu). Boards → buckets → a bucket's cards and images → a card, one screen at a time, each an address (`bucketPath`/`imagePath` in `board/links.ts`; the desktop shows the board for those). It reuses the desktop's parts: `Card`, `ComponentFrame` and `BoardImageView` without a position lay out in a list, and `PickerWindow` is a bottom sheet under the `MobileLayout` context. Changes go through `board/ops.ts` (request plus undo step, spread into `run`/`settle`), shared with the board and the card's canvas: add new card, component, image and tag changes there so both layouts get them. Navigate with `mobile/nav.ts` (`navigate`, `back`), not by setting the hash. Everything pinned to the bottom adds `env(safe-area-inset-bottom)`; use `100dvh`, not `100vh`.
- Linting is oxlint (`.oxlintrc.json`), not ESLint. TypeScript is strict about unused locals and parameters, and `verbatimModuleSyntax` requires `import type` for type-only imports.
